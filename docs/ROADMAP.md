## 3. AI-детекция на видеокарте

### Текущее состояние

Детектор работает на CPU через `ultralytics` с YOLOv8n:

```
RTSP → go2rtc → ffmpeg (1 кадр/с) → NATS → YOLOv8 → NATS → PostgreSQL
```

Замер на стенде (48 ядер Xeon E5-2673 v3, без видеокарты): детектор
занимает 220–300% процессора при 24 камерах с частотой 1 кадр/с и
включённым распознаванием лиц и номеров.

Сборка с CUDA существует (`docker-compose.gpu.yml`, `install.sh --gpu`),
но на объекте видеокарты нет, поэтому путь на живом железе не проверялся
после последних изменений.

### Цель

Обрабатывать 30–50 камер с частотой 5–10 кадров/с на одной карте.

### Варианты

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **PyTorch + CUDA (как сейчас)** | Ничего не меняется в коде, уже собрано | Тяжёлые зависимости, много видеопамяти | ✅ Оставить |
| ONNX Runtime + CUDA | Меньше памяти, стабильный API | Экспорт модели и своя пред/постобработка | ⬜ Если не хватит скорости |
| TensorRT | Наивысшая производительность | Жёсткая привязка к версии карты и драйвера | ⬜ Для максимальной нагрузки |

Решение прежнее: остаёмся на PyTorch, потому что сборка уже есть и
проверена на P104-100. ONNX — следующий шаг, если упрёмся в скорость.

### Что мешает прямо сейчас

Батчинг кадров (`BATCH_SIZE`) в текущем коде **не реализован**: кадры
обрабатываются по одному. На CPU это не критично, на видеокарте —
главный резерв производительности.

### Этапы

**Этап 1. Замеры на целевой карте (2–3 дня)**
- Собрать `docker-compose.gpu.yml`, зафиксировать кадров/с и память.
- Проверить, что детекция идёт с субпотока, а лица и номера не душат карту.

**Этап 2. Батчинг (1–2 недели)**
- Собирать кадры от разных камер в пакет 8–16 штук.
- Сохранить изоляцию трекеров по камерам (она уже есть в `main.py`).
- Замерить прирост; при провале вернуть покадровую обработку.

**Этап 3. Эксплуатация (3–5 дней)**
- Метрики: загрузка карты, очередь кадров, пропущенные кадры.
- Поведение при пропаже карты: откат на CPU с уведомлением.

## 4. Интеграция с Home Assistant

### Цель

Видеть камеры и события в умном доме, открывать двери из автоматизаций.

### Что уже готово со стороны сервера

- REST API для камер, событий, архива, СКУД.
- Поток событий SSE (`/events/stream`) — подписка без опроса.
- Вебхуки на события — можно направить в Home Assistant напрямую.
- Стабильные идентификаторы камер и контроллеров.

То есть **отдельный WebSocket не нужен**: SSE и вебхуки закрывают задачу.

### Вариант интеграции

| Подход | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Своя интеграция (HACS)** | Нативные сущности, события в шине, автоматизации по устройству | Нужно сопровождать Python-код | ✅ Основной |
| Вебхук NVR → `webhook`-триггер HA | Без разработки, работает сегодня | Нет сущностей камер, только события | ⬜ Быстрый старт |
| Generic Camera + REST sensors | Ноль разработки | По одной камере, без событий | ⬜ Для одиночных камер |

### Сущности

| Платформа | Сущность | Описание |
|---|---|---|
| `camera` | `camera.<имя>` | Поток камеры (HLS) |
| `binary_sensor` | `binary_sensor.<имя>_motion` | Движение за последние N секунд |
| `sensor` | `sensor.nvr_cameras_online` | Камер онлайн |
| `sensor` | `sensor.nvr_events_24h` | Событий за сутки |
| `sensor` | `sensor.nvr_disk_used` | Занято на диске, % |
| `switch` | `switch.<дверь>` | Открытие двери |
| `event` | `event.<имя>_detection` | Событие детекции |

### Этапы

**Этап 1. Базовая интеграция (2 недели)**
- `manifest.json`, настройка через интерфейс, координатор.
- Сущности `camera` и `binary_sensor` движения, датчики статистики.

**Этап 2. События через SSE (1 неделя)**
- Подписка на `/events/stream` вместо опроса.
- Публикация в шину HA, триггеры для автоматизаций.

**Этап 3. Управление (1 неделя)**
- Открытие дверей, кнопки перезапуска стримера.
- Публикация в HACS, README с примерами.

### Быстрый старт без интеграции

Уже сегодня событие можно отправить в Home Assistant вебхуком:

```yaml
# configuration.yaml в Home Assistant
automation:
  - alias: "Свет при обнаружении человека"
    trigger:
      - platform: webhook
        webhook_id: nvr_person
        allowed_methods: [POST]
        local_only: true
    condition:
      - condition: template
        value_template: "{{ trigger.json.object_class == 'person' }}"
    action:
      - service: light.turn_on
        target:
          entity_id: light.porch
```

## 6. Открытые вопросы

1. **Telegram недоступен с объекта.** Прямое соединение с
   `api.telegram.org` не проходит, прокси `socks5://192.168.1.1:2080`
   обрывает рукопожатие. Нужно решение владельца сети: другой прокси,
   разрешение в межсетевом экране или отказ от Telegram в пользу push.
2. **Видеокарта.** На объекте её нет, а порог `gpu_offline` включён —
   приходит ложная тревога. Пока карты нет, порог стоит выключить.
3. **Глубина архива.** Сейчас 8 дней при ~520 ГБ в сутки. Политика по
   свободному месту (а не только по возрасту) не реализована.
4. **Резервное копирование.** Бэкап БД и конфигов делается вручную;
   автоматизации нет.
5. **Масштабирование.** При 50+ камерах понадобится разделение
   медиасерверов; сейчас всё на одной машине.
